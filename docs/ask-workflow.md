# 问答生成工作流

控制台在「模型问答」切到「生成工作流」后，输入任务并发送，会调用 `POST /api/chats/{session_id}/workflow`。实现在 `backend/app/api/routers/conversations.py` 的 `propose_workflow`。

## 会做什么、不会做什么

- **会**：按任务描述让模型输出一条工作流 JSON；写入待审批记录；在对话里展示草案摘要；可改名、改节点后再审批。
- **不会**：立刻出现在工作流列表；不会带上会话历史；不会把当前智能体的完整 system prompt 当作起草提示词。

审批通过后，草案以 **已发布**（`release=published`）写入工作流表，并授给该部门。拒绝则不入库。

## 选不同智能体时提示词是否一致

**起草用的 system 模板一致。** 差别只有：

| 项 | 行为 |
|---|---|
| 模型 | 优先当前智能体版本绑定的模型；否则取本部门已授权、已启用、非 `rules` 里单价更高的模型 |
| 归属 | 审批与轨迹的 `agent_id` 为当前选中智能体 |
| 名单 | 该智能体所在部门的全部智能体；每行职责取最新版本 system prompt 的第一行（最多 80 字） |

发给模型的消息只有两条：`system` + `user`（任务原文）。工具列表为空。

## 完整输入示例

假设客服中心已有编排者、规划者、写作者、审稿人等，用户输入退款交接任务。请求体等价于：

```json
[
  {
    "role": "system",
    "content": "根据任务描述设计一条工作流，只输出一个 JSON 对象，不要解释。\nkind 用 agents 表示按连线依次执行，用 autonomous 表示第一个节点调度后面的成员。\nnodes 里只写 agent_id，必须来自下面的编号。至少两个节点。edges 用 src、dst，节点编号按出现顺序写成 n1、n2。\n可用智能体：\n- 4 编排者：编排者已接单。未点名的子任务由编排者自己执行。句子里出现规划者、研究员、写作者、审稿人或执行者时，分发给对应角色。\n- 5 规划者：规划者已列出步骤。顺序是检索、起草、核对，再交给执行者处理可计算的部分。\n- 7 写作者：写作者已完成草稿。写作者只负责成稿，不负责检索和终审。\n- 8 审稿人：审稿人已完成核对。审稿人检查是否有依据、是否跑题，不直接改业务数据。\n（同部门其余智能体同样一行）"
  },
  {
    "role": "user",
    "content": "请为客服中心「要把一笔退款交给财务部处理」起草一条工作流。节点依次用规划者、写作者、审稿人，并在流程里计算 80 + 48。"
  }
]
```

模型应只返回 JSON，例如：

```json
{
  "name": "生成的工作流",
  "kind": "agents",
  "nodes": [{"agent_id": 5}, {"agent_id": 7}, {"agent_id": 8}],
  "edges": [{"src": "n1", "dst": "n2"}, {"src": "n2", "dst": "n3"}]
}
```

`_parse_workflow` 会校验 `agent_id` 必须落在本部门目录里，至少两个节点，并补全缺省连线与摘要。载荷里还会带上 `task`（原任务）和 `chat_session_id`，供审批页与问答互跳。

## 与真正执行的关系

起草只决定「谁按什么顺序参与」。各节点执行时的提示词、工具、知识库和技能，在工作流画布或「执行」对话框里配置；定时执行还会检查已发布状态、部门 token 额度和可选的定时 token 上限。见主文档 README 的「工作流」一节与 [autonomous-agent.md](autonomous-agent.md)。

## 相关接口

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/chats/{id}/workflow` | 起草并创建待审 |
| PATCH | `/api/approvals/{id}` | 待审时改 `name`、`definition` |
| POST | `/api/approvals/{id}/decision` | 通过则入库并发布；拒绝则不入库 |
| GET | `/api/workflows/{id}/run-estimate` | 执行前模型与费用参考 |
| POST | `/api/workflows/{id}/publish` | 草稿发布 |
