# 构建自主决策的智能体

固定步骤工作流按连线依次把上一步的输出交给下一步。自主调度先把用户的一句话拆成子任务列表，再决定每一条由调度者自己执行，还是分发给画布上的下游智能体。

调度规则写在代码里，不由模型输出 JSON 计划。被分到任务的智能体仍然走自己的 `execute_agent`：计算、检索、列目录、写入和对话，按这条子任务的文字重新判断。

## 两种执行方式

保存工作流时，执行方式写入 `definition.kind`。`run_workflow` 先看这个字段。

| | 固定步骤 `agents` | 自主调度 `autonomous` |
|---|---|---|
| 入口 | `run_workflow` → `_run_agent_graph` | `run_workflow` → `_run_autonomous` |
| 节点顺序 | 沿连线走，没有入边的节点是起点 | 先规划完整列表，再按列表下标执行 |
| 交给智能体的话 | 上一步的输出；第一步是用户原文 | 这一条子任务的原文 |
| 日志事件 | `调用`、`暂停`、`停止`、`继续` | `规划`、`自己执行`、`分发`、`暂停`、`停止`、`继续` |
| 连线的含义 | 执行顺序 | 调度者可以分发给谁 |

两种图的节点类型都是 `agent`。所以 `run_workflow` 必须先判断 `kind == "autonomous"`，不能只看节点类型。

界面在 `frontend/src/views/Workflows.vue`。执行方式选「自主调度：先拆子任务，再自己做或分发」时，`definitionOf()` 把 `kind` 写成 `autonomous`。

## 在界面上建一个

1. 在智能体页准备好调度者和下游。下游的名称要能原样出现在用户句子里，例如「接待」。名称互相包含时，更长的名称优先。
2. 给调度者勾选它自己要调用的工具。自己执行「计算 19*7」时，调度者的版本里必须有 `calculator`。下游只处理对话时，可以不勾工具。
3. 打开工作流，新建，执行方式选自主调度，保持启用。
4. 先把调度者拖进画布。保存时 `entry` 是节点数组的第一项，也就是最先拖进去的智能体。界面上标「调度」的是没有入边的节点。先放调度者，这两处才是同一个智能体。
5. 再拖入下游智能体。从调度者右侧端口拖到下游节点，松开后出现连线。点击连线可去掉。
6. 保存。
7. 试运行写成多条子任务，例如 `计算 19*7；请接待说你好`。
8. 在执行页打开这次运行。第一条日志是「规划」，内容是子任务 JSON。随后是「自己执行」或「分发」。

没有从调度者连出的边时，画布上其余智能体都会成为候选。连出边之后，只有这些下游能被点名分发。

停用的工作流不能执行，也不能继续。

智能体如果在输出里用 `<<<FILE 相对路径>>>` 和 `<<<END>>>` 包住文件，或在 Markdown 代码块的语言后面写上相对路径，执行记录会收集这些文件。查看执行详情时可以下载项目压缩包，接口是 `GET /api/workflow-runs/{id}/archive`。路径不能包含 `..` 或隐藏目录。

## 定义长什么样

`POST /api/workflows` 的 `definition`：

```json
{
  "kind": "autonomous",
  "entry": "lead",
  "nodes": [
    {"id": "lead", "type": "agent", "agent_id": 1},
    {"id": "hand", "type": "agent", "agent_id": 2}
  ],
  "edges": [{"src": "lead", "dst": "hand"}]
}
```

`agent_id` 必须属于当前空间。`entry` 指向调度者节点。`edges` 只表示分发候选，不表示固定顺序。

## 规划：`_split_clauses` 和 `_plan_tasks`

文件：`backend/app/services/runtime/workflow.py`。

`_split_clauses` 把用户消息切成子任务，规则按这个顺序：

1. 消息为空，得到空列表。
2. 用 `(?:^|\n)\s*\d+[\.、]\s*` 按编号行切开。切出两条及以上才采用。`1. 计算 19*7` 换行 `2. 请接待说你好` 会变成两条。
3. 否则按换行、`；`、`;`、`然后`、`并且`、`同时` 切开。
4. 什么都切不开时，整句作为一条。

`_plan_tasks` 给每一条分配执行者：

1. 候选按名称长度从长到短排序。
2. 子任务文字包含某个候选的 `name`，就分给它。
3. 名称都没出现，再看 `key` 是否出现在文字里。
4. 都没有，执行者就是调度者，`decision` 为「自己执行」。
5. 分给下游时，`decision` 为「分发」。

每条任务的结构是：

```json
{"title": "计算 19*7", "agent_id": 1, "agent_name": "客服助手", "decision": "自己执行"}
```

`计算 19*7；请接待说你好` 在调度者叫「客服助手」、下游叫「接待」时，第一条自己执行，第二条分发给接待。句子里没有「接待」时，两条都由调度者自己执行。

这不是模型阅读任务后做的规划。要改拆分符号或匹配方式，就改这两个函数。

## 执行：`_run_autonomous`

同文件。`run_workflow` 在空间令牌未超限、且 `definition.kind == "autonomous"` 时进入它。

1. 只保留 `type == "agent"` 的节点。没有这种节点时拒绝，提示「工作流没有可调度的智能体」。
2. `_entry_node` 取调度者：`entry` 在节点里就用它，否则用没有入边的节点。
3. `_person` 读取该智能体。不属于本空间则拒绝。
4. 候选来自调度者连出的边。没有这种边时，用除调度者以外的全部智能体节点。
5. 新运行调用 `_plan_tasks`，写入一条 `event` 为「规划」的日志。`output` 是计划的 JSON。游标 `cursor` 从 `"0"` 开始。
6. 按游标取出子任务，对 `agent_id` 调用 `execute_agent`。传给它的 `message` 是子任务标题，不是上一条的输出。
7. 日志 `event` 使用计划里的 `decision`（「自己执行」或「分发」）。运行输出追加一行：`决策 · 智能体名：结果`。
8. 该步状态不是 `completed` 时，整次运行停在这个状态。高风险写入挂起后，后面的子任务不会继续。
9. 全部完成后状态为 `completed`，游标清空。

`carry_text` 会记下最近一次输出，但下一条子任务不会把它当作输入。固定步骤图才会把上一步输出交给下一步。

继续运行时，`_saved_plan` 从日志里找「规划」并还原列表，不按新消息重新规划。

## 子任务里智能体还会再决策

分发只决定谁来做。做什么仍由 `execute_agent` 决定。连得上的模型进入工具循环，同一段对话里相同工具和相同参数成功后不再调用；规则模型才按 `classify_intent` 做下面这张表：

| 子任务文字 | 意图 | 需要该智能体开放的工具 |
|---|---|---|
| 含「计算」或算术式 | calculate | calculator |
| 含「列出文件」「哪些文件」「文件夹」「目录」 | list | files.list |
| 含「知识」「规定」「退款」「文档」 | retrieve | knowledge.search |
| 含「转账」「付款」「写入」「发送」「删除」 | write | ledger.transfer |
| 含「转交」或「专员」 | delegate | 智能体自己的子智能体配置，只转一层 |
| 其余 | chat | 无。规则模型会回系统提示的第一句 |

「请接待说你好」不含上表关键词，接待智能体走对话。测试里它的系统提示是「接待已收到。」，所以结果里能看到这句话。

「退款」会判成检索。不要用带「退款」的句子去触发一个只负责对话的下游，除非那个下游开放了 `knowledge.search`。

智能体配置里的子智能体转交，和这里的「分发」不是一条路径。分发看的是工作流画布上的节点和名称；转交看的是消息里的「转交」「专员」以及智能体版本里的子智能体。

## 暂停、停止、继续

执行页的按钮写在进程内的 `RUN_CONTROL`。每完成一条子任务，若后面还有任务，`_await_control` 最多等 0.8 秒，看有没有暂停或停止。

- 暂停：状态 `paused`，游标停在下一条尚未执行的下标，日志事件「暂停」。
- 停止：状态 `stopped`，日志事件「停止」。
- 继续：`POST /api/workflows/{id}/resume` 读回原计划，日志先写「继续」，再从游标执行。

接口也可以在运行时带 `pause_after`。完成这么多条子任务后主动暂停。测试 `test_autonomous_workflow_splits_and_assigns` 用 `pause_after: 1` 停在第一条「自己执行」之后，再继续，最后一条日志是「分发」给接待。

## 和固定步骤对照着改

固定步骤在 `_run_agent_graph`：

- 游标是节点 id，不是子任务下标。
- 每步 `message` 使用 `carry_text`，第一步是用户原文。
- 走完一条出边后进入下一个节点，最多 8 步；同一节点出现超过两次会熔断。
- 日志事件是「调用」。

要把固定流转改成自主调度，不需要换节点类型。把 `kind` 改成 `autonomous`，并保证 `entry` 是调度者。已保存的固定步骤工作流保持 `kind` 为 `agents` 时，行为不变。

## 想让规划更智能时改哪里

当前计划完全由标点和名称匹配产生。若要改成调度者调用模型生成子任务列表，只替换 `_plan_tasks` 的返回值。`_run_autonomous` 要求每一项都有 `title`、`agent_id`、`agent_name`、`decision`。`decision` 为「分发」或「自己执行」，并写入日志。`agent_id` 仍应来自候选或调度者，避免计划指向画布以外的智能体。

拆分符号只改 `_split_clauses`。分发对象的匹配只改 `_plan_tasks` 里按名称、按 key 选择的两行。
